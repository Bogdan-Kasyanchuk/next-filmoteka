## Context

Мотивація — див. `proposal.md` → Why. Вимоги — див. `specs/tv-episode-page/spec.md`.

Технічний стан, який формує підхід:

- Detail-сторінки застосунку побудовані за одним шаблоном: server-компонент `page.tsx` робить `queryClient.prefetchQuery`, перевіряє результат через `getQueryData` → `notFound()`, віддає `HydrationBoundary` навколо клієнтського `Content`, який тими самими ключами читає дані через `useQuery` / `useQueries` і мапить їх через `helpers/transformData`.
- `fetchApi` (`src/services/tmdb/api.ts`) на сервері бʼє напряму в TMDB з `api_key`, на клієнті — через проксі `/api/tmdb`; 404 уже перетворюється на `notFound()`, інші помилки кидаються як `Error`.
- Сторінка сезону вже прогріває два ключі: `tvShowsQueryKeys.currentTvShowById(id, locale)` і `tvShowsQueryKeys.seasonById(id, season, locale)`.
- Спільні компоненти `components/app/Videos`, `Reviews`, `Recommendations` жорстко типізовані під `MediaType.MOVIE | MediaType.TV_SHOW` і самі роблять `useSuspenseQuery`.
- Рядки інтерфейсу витягуються автоматично: `next-intl` `experimental.extract` генерує хешовані ключі в `src/messages/en.json` під час dev/build; `uk.json` заповнюється вручну.
- CSS — БЕМ-подібні класи з префіксами `p-` (page) і `c-` (component), файли `styles/{index,page,components}.css` поруч зі сторінкою.

## Goals / Non-Goals

**Goals:**

- Сторінка епізоду не відрізняється від решти detail-сторінок за структурою, іменуванням і поведінкою — її можна читати як `seasons/[season]`.
- Усі правки, крім однієї, адитивні: нові функції, типи, ключі й файли, без зміни сигнатур наявних.
- Один мережевий круг за деталями епізоду.

**Non-Goals:**

- Не рефакторимо спільні `Videos` / `Reviews` / `Recommendations` під епізоди.
- Не додаємо секції рецензій і рекомендацій — TMDB не має таких ендпоінтів для епізоду.
- Не додаємо `generateStaticParams` / ISR — інші detail-сторінки їх теж не мають.
- Не чіпаємо сторінку сезону, крім передавання нових пропсів у `EpisodeCard`.

## Decisions

### 1. Деталі епізоду — один запит з `append_to_response=images`

`GET /tv/{id}/season/{s}/episode/{e}` уже повертає `crew` і `guest_stars` у базовій відповіді, тож `credits` не потрібен — достатньо дописати `images`. Один виклик `fetchApi` дає деталі епізоду, гостьових зірок, команду й кадри.

Відео свідомо лишаються поза цим запитом: вони вантажаться окремо, щоб можна було перевикористати спільний `components/app/Videos` (рішення 5).

*Альтернатива:* дописати ще й `videos`. Відкинуто: тоді дані вже були б на сторінці, а спільний компонент сам робить запит — довелося б або дублювати його розмітку локально, або ігнорувати вже завантажені дані.

*Наслідок:* деталі, гості, команда й галерея приходять разом і рендеряться під один `Loader`, як на сторінці сезону, а секція відео стрімиться окремо під `Suspense`, як на сторінках фільму й тв-шоу.

### 2. Сторінка самодостатня: три ключі прогріваються нею самою

`page.tsx` прогріває всі три ключі власноруч, без припущень про те, звідки прийшов користувач:

| Ключ | Навіщо |
| --- | --- |
| `tvShowsQueryKeys.currentTvShowById(id, locale)` | назва серіала для хлібних крихт і метаданих |
| `tvShowsQueryKeys.seasonById(id, season, locale)` | назва сезону + список епізодів для навігації попередній/наступний |
| `tvShowsQueryKeys.episodeById(id, season, episode, locale)` | деталі епізоду |

Перші два ключі збігаються з ключами сторінки сезону, тож при клієнтському переході «сезон → епізод» React Query віддає їх із кешу. Це оптимізація, а не умова роботи: при вході прямим лінком, із закладки чи після перезавантаження сервер прогріває ті самі три ключі з нуля, і сторінка поводиться однаково.

*Альтернатива для навігації:* рахувати сусідів як `episode ± 1` без списку епізодів. Відкинуто: нумерація епізодів у TMDB буває з пропусками, і без списку неможливо визначити останній епізод сезону — вимога «на останньому епізоді перехід недоступний» не виконувалась би.

### 3. Ключ епізоду в `queryKeys`

`episodeById: (id, season, episode, locale) => [ 'tv-shows', id, season, episode, locale ]` — продовжує наявний `seasonById: [ 'tv-shows', id, season, locale ]`, тож ключ епізоду не перетинається з ключем сезону.

### 4. Схема й маппер епізоду

- `EpisodeDetailsShema` — самостійний тип (не перетин з `EpisodeShema`), що повторює всі поля `EpisodeShema` **крім `show_id`** і додає `images: { stills: ImageShema[] }`. Без `videos` — відео завантажуються окремо (рішення 5), у шему не входять.
- `EpisodeDetailsMapper.episode` — inline-об'єкт із тими самими полями, що й `EpisodeMapper`, а не посилання на сам тип `EpisodeMapper`. Це узгоджує епізод із наявним патерном `SeasonDetailsMapper.season`, який так само дублює поля `SeasonMapper` inline, а не посилається на нього.
- `transformTVShowEpisodeDetails()` повертає `EpisodeDetailsMapper` з полями `episode`, `guest_stars`, `crew`, `images` — за формою `transformTVShowSeasonDetails` і `transformPersonDetails`.
- Наявний приватний `transformEpisode` перевикористовується для деталей епізоду, тож його параметр розширено з `EpisodeShema` до `Omit<EpisodeShema, 'show_id'>` — функція ніколи не читала `show_id`, тож звуження вимоги безпечне й сумісне з наявним викликом (`SeasonDetailsShema.episodes: EpisodeShema[]`, де `show_id` є, просто ігнорується).
- `guest_stars` мапиться наявним `transformCast` (тип `Omit<CastShema, 'cast_id'>` сумісний із полями, які читає маппер), `crew` — наявним `transformCrew`, `stills` — наявним `transformImage`.

### 5. Відео епізоду — спільний `app/Videos` плюс `MediaType.EPISODE`

Наявний `components/app/Videos` підходить як є: він сам робить `useSuspenseQuery`, сам відбирає YouTube-ролики типів `Trailer` і `Clip`, сам ховає себе на порожньому результаті й має готовий `VideosSkeleton`. Бракує лише шляху до епізодного ендпоінта. Тому замість локальної копії розширюються три точки:

1. `enums.ts` — `MediaType.EPISODE = 'episode'`.
2. `services/tmdb/general.ts` — `getVideos(type, id, locale, episode?)`: для `MediaType.EPISODE` шлях будується як `tv/{id}/season/{season}/episode/{number}/videos`, для решти лишається `{type}/{id}/videos`.
3. `helpers/queryKeys.ts` — `generalQueryKeys.videos` додає в ключ номери сезону й епізоду, коли вони передані, щоб відео різних епізодів не ділили один ключ.

Пропси `Videos` стають union: гілка `MediaType.MOVIE | MediaType.TV_SHOW` з `id` (наявні виклики зі сторінок фільму й тв-шоу компілюються без правок) і гілка `MediaType.EPISODE`, де координати епізоду обовʼязкові. Так неможливо запросити відео епізоду, не вказавши сезон і номер.

Сторінка епізоду підключає компонент так само, як сторінки фільму й тв-шоу: `<Suspense fallback={ <VideosSkeleton /> }>`.

*Альтернатива:* локальний презентаційний `Videos.tsx` у папці сторінки, який отримує вже завантажений список пропсами (тоді відео приходили б у `append_to_response`). Відкинуто: дублює розмітку секції та правило відбору роликів, тож дві секції відео могли б розʼїхатися.

*Трейд-оф:* `MediaType.EPISODE` — не справжній TMDB `media_type` (див. Ризики), а окремий запит додає ще один круг замість `append_to_response`. Прийнятно: секція стрімиться під `Suspense` і не затримує решту сторінки.

### 6. Галерея кадрів

Локальний `Gallery.tsx` за зразком `persons/[id]/components/Gallery.tsx`, на наявному `ImageCard`, з класами `p-episode__gallery*`. `ImageCard` отримує новий опційний проп `size` (за замовчуванням — наявний `IMG_SIZES.PERSON_IMAGE`, як і раніше), бо кадри епізоду мають інше співвідношення сторін (16×9), ніж фото персони (2×3), і потребують окремого розміру (`IMG_SIZES.EPISODE_IMAGE`). Проп опційний і зворотньо сумісний — сторінка персони, єдиний наявний споживач, поведінки не змінює.

### 7. Клікабельна `EpisodeCard` — stretched link

`EpisodeCard` отримує два нові обовʼязкові пропси — `tvShowId` і `season` — і всередині рендерить `Link` на `pagesEpisodeUrl(...)`, розтягнутий на всю картку через абсолютний оверлей, а не обгортку всього вмісту.

Причина: у картці вже є `<button>` тригера поповера. Вкладати `<button>` у `<a>` — невалідний HTML і зламана клавіатурна навігація. Stretched link лишає посилання єдиним інтерактивним елементом «фону» картки, а тригер поповера піднімається над оверлеєм через `z-index` і працює як раніше.

*Альтернативи:* обгорнути картку в `Link` (невалідна вкладеність) або повісити `onClick` з `router.push` на контейнер (втрата семантики посилання, немає відкриття в новій вкладці, гірша доступність). Обидві відкинуто.

Пропси зроблено обовʼязковими, а не опційними: єдине місце використання картки — сторінка сезону, і там обидва значення відомі; опційність лишила б мовчазний шлях, де картка не веде нікуди.

### 8. Розміри зображень

Додаються `IMG_SIZES.EPISODE_DETAILS_COVER = 'w780'` (кадр у шапці, формат 16×9) і `IMG_SIZES.EPISODE_IMAGE = 'w300'` (мініатюри галереї) — поруч із наявним `EPISODE_COVER`.

### 9. Метадані

`generateMetadata` копіює форму сторінки сезону: `getCurrentTVShowById` + `getTVShowEpisodeByNumber`, далі `generateMetaTags` з `pagesEpisodeUrl(...)`. `getTVShowEpisodeByNumber` обгортається в `cache()` — інакше `generateMetadata` і `Page` зробили б два однакові запити.

### 10. Валідація сегментів маршруту

`season` і `episode` парсяться в число; якщо `Number.isInteger` не виконується — одразу `notFound()`, не чекаючи відповіді TMDB. Це закриває сценарій «нечисловий номер» і не дає зібрати сміттєвий URL до TMDB.

### 11. Клієнтський проксі `/api/tmdb` — розширення allowlist (виправлення знайденого дефекту)

`src/app/api/tmdb/[...path]/route.ts` фільтрує шляхи через `ALLOWED_PATH_PATTERNS` — білий список regexp для захисту від проксіювання довільних TMDB-ендпоінтів. У списку були патерни для `tv/{id}/season/{s}`, але не для `tv/{id}/season/{s}/episode/{e}` і `.../episode/{e}/videos`. Це виявилося під час ручного тестування: сторінка епізоду рендерилась на сервері нормально (`fetchApi` на сервері звертається до TMDB напряму), але клієнтський `Videos` (рішення 5, завжди клієнтський запит) отримував 404 від проксі, що через `notFound()` валило всю сторінку.

Виправлення — додати два патерни до `ALLOWED_PATH_PATTERNS`:
```
/^tv\/\d+\/season\/\d+\/episode\/\d+$/,
/^tv\/\d+\/season\/\d+\/episode\/\d+\/videos$/,
```
Без цього вимога «Секція відео епізоду» і «Самодостатність сторінки при прямому вході» не виконувались би на практиці для будь-якого клієнтського переходу чи прямого входу — сторінка епізоду взагалі не працювала б у продакшн-подібному режимі (де `Videos` завжди йде через клієнтський проксі).

### 12. Візуальне вирівнювання з `MovieDetails`

За результатами рев'ю сторінка деталей епізоду перероблена так, щоб типографіка й елементи UI відповідали `movies/[id]/components/MovieDetails.tsx`, а не залишалися довільним варіантом у стилі `CurrentSeason`:

- **Фон на весь блок**: `.p-episode__current-episode-backdrop` — той самий кадр епізоду (`still_path`), розтягнутий на всю ширину блоку й затемнений, за патерном `.p-movie__details-backdrop`.
- **Рейтинг/голоси/тривалість — круглі елементи**, а не прямокутні теги: `.p-episode__current-episode-list-rounds`, перша кругла позначка з conic-gradient за відсотком рейтингу (як у `MovieDetails`), решта — прості кола з `radial-gradient` та рамкою. У епізода немає `popularity` (TMDB не повертає це поле для епізодів), тож кіл три (рейтинг, голоси, тривалість) замість чотирьох у фільма.
- **Рік поруч із назвою**: `{episode.name} ({рік з air_date})` — той самий патерн, що `{movie.title} ({рік з release_date})` у `MovieDetails`.
- **Хлібна крихта серіал/сезон**: назва серіала й «Сезон {N}» — окремі посилання, розділені `/`, одним рядком над заголовком; номер сезону більше не дублюється окремим прямокутним тегом.
- **Список деталей у форматі ключ:значення** (`.p-episode__current-episode-list-info`, шрифт `--text-lg` на десктопі) замість прямокутних тегів — той самий патерн, що `.p-movie__details-list-info` (Budget/Revenue/Genres тощо).
- **Опис — унизу, на всю ширину**, після всього іншого контенту — як `.p-movie__details-overview`.

### 13. Кнопки «попередній/наступний епізод» — під кадром, без стрілок, колір/фон/бордер/ховер як у кнопки «Схожі фільми»

Кнопки лишаються під кадром епізоду (а не поруч чи угорі, як міркувалось спочатку) — це свідомий вибір компонування, відмінний від `MovieDetails` (де під постером лише одна кнопка «Схожі фільми»), бо в епізода їх завжди дві. Іконку стрілки (`Icon name="arrow"`) прибрано — лишається тільки текст «Previous episode» / «Next episode», компактніше під вузьким кадром і без потреби у власному напрямку іконки для prev/next.

Колір, фон, бордер і ховер скопійовані з `.p-movie__details-similar-button`:
- бордер: `1px solid color-mix(in oklab, var(--color-primary) 75%, transparent)`
- фон: `color-mix(in oklab, var(--color-secondary) 75%, transparent)`
- ховер: `color: var(--color-secondary)`, фон стає `color-mix(in oklab, var(--color-primary) 75%, transparent)`

Розмір, падінги й розташування (два компактні кнопки в ряд під кадром) лишаються власними — тільки колірна схема запозичена, оскільки контекст (дві вузькі кнопки під невеликим 16:9-кадром) інший, ніж одна широка кнопка на постері фільму.

### 14. Мобільне розташування кругових індикаторів — `display: contents`

На екранах до 768px круглі індикатори (рейтинг/голоси/тривалість) мають стояти праворуч від кадру й кнопок навігації одним вертикальним стовпчиком — так само, як на мобільній версії `MovieDetails` (де `.p-movie__details-list-rounds` стоїть у вузькій другій колонці поруч із постером). На десктопі ті самі кола повертаються у звичайний потік між заголовком і списком деталей, одним блоком з хлібною крихтою й заголовком.

Технічна складність: одна й та сама розмітка має по-різному групуватися залежно від брейкпоінта — на мобільному колам потрібно «вийти» зі спільного блоку з хлібною крихтою/заголовком/списком деталей і стати самостійним grid-елементом поруч із кадром; на десктопі всі чотири елементи (хлібна крихта, заголовок, кола, список деталей) мають бути одним компактним flex-стовпцем.

Рішення — обгортка `.p-episode__current-episode-info` з `display: contents` за замовчуванням (мобільно: діти стають прямими grid-елементами контейнера `.p-episode__current-episode-container`, і кожен позиціюється власним `grid-column`/`grid-row`, включно з колами, які через `grid-row: 1/3` розтягуються на висоту кадру+кнопок) і `display: flex; flex-direction: column` від `--min-md` (десктоп: обгортка сама стає ОДНИМ grid-елементом, що охоплює рядки кадру й кнопок навігації, а її вміст — хлібна крихта, заголовок, кола, список — тече звичайним flex-стовпцем усередині).

*Чому не окремі `grid-row` для кожного елемента на десктопі теж* (як у першій ітерації правки): якщо хлібна крихта й заголовок займають ті самі grid-рядки, що кадр і кнопки навігації, розмір рядка визначається найвищим елементом у рядку (`grid-template-rows: max-content`) — рядок хлібної крихти розтягується до висоти кадру (~190px), а рядок кнопок навігації — до висоти заголовка (великий шрифт `--text-6xl`). Це проявлялось як великий порожній проміжок між хлібною крихтою і заголовком і неприродно високі кнопки навігації (`align-self: stretch` за замовчуванням розтягує їх на всю висоту «свого» рядка). `display: contents` на десктопі усуває цю проблему, бо кола/заголовок/список більше не займають ОКРЕМІ рядки, які поділяються з кадром/кнопками — вони течуть усередині одного flex-елемента, чия висота визначається його власним вмістом.

## Risks / Trade-offs

- **Правка `EpisodeCard` ламає сторінку сезону, якщо забути передати нові пропси** → пропси обовʼязкові, тож `tsc --noEmit` впаде на етапі збірки, а не в рантаймі.
- **Stretched link може перекрити тригер поповера** → тригеру задається `position: relative` і `z-index` вище за оверлей; сценарій «поповер лишається робочим» перевіряється вручну в браузері.
- **`MediaType.EPISODE` не є валідним TMDB `media_type`** — TMDB не має ні `trending/episode`, ні `search/episode`, тож нове значення осмислене лише для шляху відео → фільтри trending і search перелічують значення `MediaType` явно (`MOVIE`, `TV_SHOW`, `PERSON`), а не через `Object.values`, тож у UI воно не зʼявиться; підроблений `?type=episode` в URL дасть 404 від TMDB так само, як будь-яке інше сміття сьогодні. Після правки enum перевірити обидва фільтри й типи `media_type` у `shemas.ts` / `types.ts`.
- **Правка спільного `Videos` зачіпає сторінки фільму й тв-шоу** → union пропсів побудований так, що наявні виклики (`type` + `id`) лишаються валідними без змін; `yarn typecheck` і ручна перевірка обох сторінок входять у задачі.
- **`append_to_response=images` збільшує відповідь епізоду** → `images.stills` для окремого епізоду рідко перевищує кілька десятків записів; це дешевше за додатковий круг.
- **Порожній `uk.json` для нових рядків** → після витягу перекладів перевірити, що жоден новий ключ не лишився з порожнім значенням.
- **Помилка запиту відео не має валити сторінку** (вимога спеки) → поведінка успадковується від спільного компонента: він повертає `null` на помилці й на порожньому результаті, а `Suspense` ізолює його завантаження від решти сторінки.
- **Клієнтський проксі блокує ще не описані в allowlist шляхи TMDB** → знайдено й виправлено для епізодних шляхів (рішення 11); за аналогією варто памʼятати про це при додаванні будь-якого нового клієнтського запиту в майбутньому — сторінка може повністю рендеритись на сервері (де проксі не задіяний) і одразу падати в браузері.
- **Розбіжність код/дизайн-документ на момент цього запису** → рішення 12–14 (вирівнювання з `MovieDetails`, кольори кнопок навігації, `display: contents` для мобільного розташування кіл) описують погоджений і раніше перевірений у браузері підхід, але на диск `CurrentEpisode.tsx` і `page.css` у якийсь момент повернулися до попередньої версії без цих правок (немає обгортки `-info`, кнопки навігації — старого кольору). Це виглядає як ненавмисне скасування правки (можливо, undo в редакторі), а не свідома зміна — перед подальшою роботою варто звірити файли з цим документом і за потреби відновити рішення 12–14.
